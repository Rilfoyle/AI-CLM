# 一诺复刻调研：角色、流程、界面与功能

> 调研日期：2026-08-27
>
> 当前结论性质：竞品现状与客户需求证据，不是已确认的新系统规格。
>
> 本轮只读分析；未在一诺测试租户创建、修改、审批或导出任何业务数据。

## 1. 结论先行

上一版 AI-CLM 的问题不是少补几个菜单，而是产品组织方式和一诺不同：当前仓库是“通用 CLM 菜单 + 单合同 ACL + 通用 BPM”的 POC；一诺页面呈现为“角色工作台 + 合同任务链 + 分阶段业务环节”。新系统需要建立能承载这些业务语义的自有对象，不能据此推断一诺内部数据模型。

一诺完整产品链和本项目第一阶段必须分开理解。需要复刻的是客户已经熟悉的使用心智；第一阶段则按用户确认，只闭环起草、协同/法务审查和合同审批：

1. 业务、法务、合同管理、用章管理、系统管理必须是不同的工作视图。
2. 一诺的完整业务主轴是同一份合同从起草、协同、审批、用章、签署、归档到变更/续签/关闭的连续任务链；新系统第一阶段在合同审批完成处截断。
3. 合同正文/详情页是共同工作界面；AI 应嵌入正文侧栏，不应先做一个脱离合同流程的独立驾驶舱。
4. “管理员”不能做成万能超管：合同管理员负责合同治理，系统管理员负责组织、账号、角色、集成和安全，默认不应读取业务合同正文。
5. 测试租户存在历史权限噪声，不能逐菜单照抄；要复刻用户流程和业务语义，再重组权限。

## 3. 本租户观察到五个产品视角

测试账号可切换 `业务员 / 法务 / 合同管理员 / 用章管理员 / 系统管理员`。审批人是流程中的参与身份，不必再做一个独立产品门户。

### 3.1 业务方（经办人）

**典型任务链**

工作台待办 → 选择模板/上传文件/复制合同/续签 → 填写合同及交易方信息 → 发起协同 → 提交审批 → 跟踪退回和进度 → 申请用章 → 跟踪我方/对方签署 → 上传线下双方盖章文件 → 等待归档确认 → 变更、续签或关闭。

**主要界面与功能**

| 界面 | 实测重点 |
|---|---|
| 角色工作台 | 审批四宫格；按生命周期分桶的任务中心；快捷起草/查询；续签和关闭提醒 |
| 融合起草中心 | 标准模板、已有文件上传、复制合同、合同续签四条入口 |
| 模板选择 | 分类、搜索、预览、适用说明、选择最新版 |
| 合同查询/台账 | 我审批的/我经办的/我发起的；多条件和保存筛选；列表/进度视图；导入导出；父子/来源关系 |
| 合同正文与详情 | 正文为主，结构化信息、交易方、签约状态、用章、交易信息、重大承诺和全生命周期记录为辅 |
| 审批中心 | 左侧任务收件箱，右侧摘要、签约流程、相关文件、审批记录、评论；任务卡直接显示关键上下文和等待时长 |
| 签约进度 | 待申请签章、待我方签约、待对方签约、已签订、已失效；纸质/电子签约及各方进度 |
| 归档中心 | 待确认归档/已完成归档；最终文件、归档地址、变更标记和确认记录 |
| 续签/关闭 | 到期提醒、续签生成、关闭处理及原合同关联 |

### 3.2 法务方

**典型任务链**

从待协同/待审批进入 → 查看交易背景、相对方和历史版本 → 对正文和结构化字段审查 → 在线修改/评论/文本比对 → 处理风险或提交意见 → 通过、拒绝、退回、转交、加审 → 持续管理模板与重大承诺。

**主要界面与功能**

| 界面 | 实测重点 |
|---|---|
| 法务工作台 | 审批四宫格；待我协同、我已协同、待我审批；模板快捷入口 |
| 协同/审批详情 | 合同上下文、正文和版本、审批动作、评论、完整审批记录 |
| 模板管理 | 草稿/已提交；模板编码、适用分类/性质、填空或全文编辑、来源、发布人、有效版本；新建、导入导出、高级配置 |
| 合同查询与详情 | 公司或授权组织范围的合同检索、版本及关系追溯 |
| 重大承诺 | 按合同汇总承诺数、逾期/未完成/已完成、责任部门和负责人 |
| AI 辅助（官方界面证据） | 智能摘要、要素抽取、敏感词、智能审查；风险项定位正文、给出建议并区分未处理/已处理。精确版本绑定是新系统的不变量建议，不是由截图推断出的后台实现 |

法务菜单还包含知识产权、纠纷、案件、律所律师和工商档案。这是“综合法务管理”扩展域，不是客户 18 条需求的合同主流程，第一期建议不复刻。

模板维护和重大承诺监督在当前灵宝租户分配给法务，但这是可配置的租户职责；目标系统仍需由用户确认法务与合同管理员的治理分工。

### 3.3 合同管理员

**目标职责建议**

维护合同分类、模板及版本、编码规则、审批/用章/归档流程、业务数据与操作权限政策、预警规则、全局合同台账和审计。系统管理员负责把技术角色分配给用户；具体治理分工仍可按租户配置。

**测试租户现状提醒**

当前 `合同管理员` 角色可见审批、合同拟制、签约进度、归档、续签/关闭和重大承诺，但模板与大量合同配置分别出现在法务或系统管理员视角。这更像租户历史配置结果，不应作为新系统的角色定义。目标产品应把合同治理能力从系统运维能力中拆回合同管理员。

### 3.4 用章管理员

**典型任务链**

收到用章申请 → 核验合同版本、签约方式、签署顺序和签约主体 → 按印章类型走用章审批 → 选择印章/签约人 → 跟踪我方和对方签署 → 处理异常或失效。

**主要界面与功能**

- 审批中心：合同审批与合同用章是不同任务类型。
- 印章管理：印章主数据、适用主体、状态和权限。
- 签约进度：纸质/电子签约、各签约方状态和完成数。
- 合同只读上下文：正文版本、签约主体、用章份数和审批历史。

客户需求 #13 明确要求合同审批通过后自动发起用章申请，并允许配置用章审批流；因此用章不是合同状态上的一个按钮，而是独立业务环节。

### 3.5 系统管理员

**典型任务链**

同步组织/员工 → 建角色并分配用户、字段和数据权限 → 配账号生命周期及安全策略 → 配钉钉/SSO/待办跳转 → 管理系统参数、日志、接口和运行状态。

**实测主要界面**

- 角色管理：角色基础信息、分配用户、客户端、工作台、字段/数据权限。
- 组织架构：公司/部门树、导入、上下级与负责人。
- 用户、菜单、登录、安全策略、LDAP、在线用户和登录日志。
- 第三方平台：钉钉登录映射、通讯录同步、工作流待办消息、单点跳转和跳转页面。
- 审计、接口与运维监控。

测试租户的系统管理员左侧出现 30 多组平台菜单，并能看到业务入口。这是实施平台的复杂度，不应暴露在第一期产品主导航；系统管理员默认也不应因此获得合同正文数据权限。

## 4. 跨角色主链路

实测页面支持的主链路可概括为：

```text
草稿/协同
  → 提交合同审批
  → 审批通过
  → 自动或手动发起用章申请
  → 用章审批
  → 我方签约 / 对方签约（纸质或电子）
  → 上传最终双方盖章文件
  → 归档确认
  → 已归档
  → 变更 / 续签 / 关闭 / 终止 / 作废
```

三个容易被上一版压扁的事实：

1. 合同审批和用章审批是两类流程实例。
2. “签署完成”“上传最终扫描件”“归档确认”是三个不同事件；合同状态和归档状态在一诺列表里分列展示。
3. 工作台的“待协同、待提交、待申请签章、待我方签、待对方签、待上传扫描件、待归档、待反馈”不是统计卡片，而是可执行任务队列。

以上是对一诺完整链路的观察，不是第一阶段范围。用户已确认第一阶段在“合同审批完成并形成获批修订”处结束，不生成用章、签署、归档或履约任务，也不把审批通过显示为已签订。

## 5. 第一阶段需要复刻的业务界面

| 复刻切片建议优先级 | 界面 | 主要角色 | 必须保留的产品语义 |
|---|---|---|---|
| P0 | 角色化工作台 | 业务、法务、审批人、合同管理员、系统管理员 | 每个角色只看自己的任务、异常和快捷入口；用章管理员第一阶段无任务 |
| P0 | 起草中心 | 业务 | 标准模板、非标上传两条主路径；复制、续签后置 |
| P0 | 合同编辑/详情中心 | 业务、法务、审批人 | 正文+结构化信息+阶段+侧栏工具，所有动作围绕同一合同 |
| P0 | 合同台账 | 业务、法务、合同管理员 | 我的口径、组织口径、保存筛选、当前审批进度和历史 |
| P0 | 审批中心/任务详情 | 业务、法务、审批人 | 合同审批上下文、正文、差异、文件、记录、评论和动作；不含用章审批 |
| P0 | 模板管理 | 法务、合同管理员 | 模板独立身份、版本、适用范围、发布和最新版 |
| P0 | 合同治理设置 | 合同管理员 | 分类、编码、审批路由和权限的有限配置；不复制通用低代码平台 |
| P0 | 相对方导入 | 合同管理员 | 解析、校验、去重、部分失败与逐行重试 |
| P0 | 组织/角色/钉钉 | 系统管理员 | 组织同步、角色数据权限、审批待办推送和深链 |
| P0 | AI 审查侧栏 | 业务、法务、审批人 | 绑定精确修订的摘要、抽取、审查和风险处理；故障不阻断人工流程 |
| P1 | 重大承诺声明 | 业务、法务 | 填写或显式确认“无重大承诺”，提交校验；履行状态、到期和证据后置 |
| 后置 | 用章、签约进度、归档中心 | 业务、用章管理员、合同管理员 | 第一阶段不展示入口、不生成任务 |
| 后置 | 变更/续签/关闭 | 业务、合同管理员 | 第一阶段不进入合同后段处置 |

这里的 P0/P1 是本次复刻切片建议，不覆盖客户附件中的 P1/P2 原始优先级。

签约进度页中出现纸质/电子两种方式，只证明一诺页面能表达这两条路径。用户已经确认第一阶段“不用到签署”，因此纸质签署状态、电子签、CA、印控和回调均后置。

## 6. 客户 18 条需求如何落到主链路

| # | P | 需求归属 | 对复刻的约束 | 尚缺的确认 |

| 14 | P2 | 审批记录 | 展示该合同全部审批历史 | “全部”是否包含用章等其他流程、撤回/驳回重提、历史版本；数据权限和展示方式 |

| 17 | P2 | 重大承诺 | 未填写不得提交 | “无重大承诺”是否需显式确认，必填字段有哪些 |

按用户确认的第一阶段边界，18 条需求的版本归属为：

- 第一期核心：#2、#4、#11、#12、#14、#16、#17。
- 第一期必要支撑：#5、#6、#7。
- 第一期部分覆盖：#1 只验收起草到审批完成的留痕，不能宣称全生命周期留痕已经完成。
- 明确后置：#3、#8、#9、#10、#13、#15、#18。

客户 P1/P2 表示原始业务优先级，不机械等同版本范围。#13 虽是 P1，仍因用户明确“不用到签署”而后置；#14、#17 虽是 P2，却分别约束审批可审计性和提交校验，因此进入第一阶段。

## 7. 当前 AI-CLM 与目标的结构性差距

### 7.1 已有可复用底座

- 合同、签约方、正文/附件和不可覆盖文档版本。
- 审批绑定精确正文版本、表单快照和 SHA 校验。
- 单合同 owner/协作人/查看人 ACL 与追加式审计事件。
- 通用 BPM 已有通过、拒绝、抄送、转办、委派、加签、退回等动作界面；评论入口虽存在，但当前前后端接口错位，不能算可用能力。
- ONLYOFFICE 在线编辑和四入口起草中心的初步外形。

这些底座应保留，但不能继续直接暴露 SHA、Binding 编号、流程 Key、冻结标记和底层权限布尔开关给业务用户；评论仍需按实际接口重新接通和验证。

### 7.2 P0 结构性缺口

1. 没有业务/法务/合同管理/用章/系统管理的合同域角色；普通角色反而拿到全部 CLM 管理权限。
2. 没有独立合同管理员角色及全局合同数据范围；`common` 虽已有类型、签约方等管理菜单，但合同列表仍只覆盖负责人和显式参与人，并漏掉仅作为流程参与人的法务审批人。
3. 生命周期从审批通过直接“上传盖章件→已签订”，没有用章申请、签约方任务、上传最终件、归档确认、变更和关闭业务对象。
4. 模板只是合同类型上的一个文件，没有独立模板、版本、变量、适用范围和发布生命周期。
5. 四路径起草只有页面外形：模板不回填变量，上传起草仍需到详情二次上传，首页还存在绕过起草中心的重复入口。
6. 通用 BPM 能操作，但不是合同任务收件箱，也没有一诺式合同摘要、签约流程、文件、完整审批记录和评论的一体化详情。

`docs/YINUO_REFERENCE.md` 的租户观察仍可作为历史素材，但其中“角色化瘦身菜单已经对齐”的判断与当前 SQL/代码不符；本文件替代其“当前系统已对齐/未对齐”的结论。

### 7.3 明显不该继续复制或暴露的内容

- 法务扩展域：案件、纠纷、知识产权、律所律师、工商档案（除非后续单独立项）。
- HIPS、开发管理、调度、接口、前置机、运维监控等平台菜单进入合同主导航。
- 通用“业务对象→字段→布局”低代码平台、通用规则引擎的完整后台；第一期只实现客户明确需要的分类、编号、审批路由和权限设置，提醒后置。
- 所有角色都能看到模板发布、表单设计、签约方删除等管理按钮。
- 详情页直接显示技术主键、哈希、流程 Key 和 ACL 开关。
- 多个“新建合同/合同拟制”入口和没有资格校验的通用“续签”按钮。
- 独立 AI 聊天页替代合同正文、审批和任务流程。

## 8. 本轮范围判断

第一阶段已经确认以“起草—协同/法务审查—合同审批完成”为边界：角色工作台、标准模板/非标上传、合同修订、AI 侧栏、合同审批、前段台账、模板/类型/编号/路由/权限治理、相对方导入、组织/角色/钉钉，以及重大承诺的填写与提交校验。

明确后置：用章、签署、最终件上传、归档、履约、到期提醒、变更、续签、关闭、综合法务管理、报表、结算/财务、通用低代码平台和开发运维平台。其中用章、纸质签约和归档虽然是客户 P1，仍因用户明确的阶段边界后置；不能以预留按钮或空页面声称完成。

AI 已确认作为第一阶段合同修订上的辅助记录与侧栏能力：摘要、要素抽取、风险审查、修改建议和处理状态都绑定具体修订，最终决定仍由人完成；AI 失败不阻断人工流程。
