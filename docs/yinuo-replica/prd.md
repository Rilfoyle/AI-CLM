> 当前阶段：信息架构已确认；用户明确跳过交互原型，进入第一版实施；2026-08-29 菜单与术语对齐已完成并通过自动化与真实浏览器验收
>
> 已确认：对象定义、角色边界、AI 形态、第一期终点、审批编辑不变量、业务流程、标准模板直提规则、编号重提语义、功能清单
>
> 原型：按用户要求取消；开发：2026-08-28 治理增量和 2026-08-29 菜单术语修订均已通过当前验收，整体按模块看板继续推进

## 1. 要解决的问题

客户已经熟悉一诺的合同工作方式。上一版 AI-CLM 虽可演示，但以技术对象、通用 BPM 和单合同 ACL 组织产品，缺少角色工作台、独立模板版本、合同治理规则、审批修订责任，以及客户提出的钉钉、编码、相对方、重大承诺等前段能力，同时暴露了过多平台和技术信息。

新系统先建立能承载相同业务语义的自有对象和角色边界。第一阶段只闭环：

**起草 → 协同/法务审查 → 合同审批完成**

合同审批完成表示形成一份获批的精确合同修订，不表示合同已用章、已签署、已生效、已归档或已进入履约。

## 2. 产品组织轴

- 业务经办人、法务、审批人：以“我的任务 + 合同”为组织轴。
- 合同管理员：以“合同全局台账 + 合同治理对象”为组织轴。
- 系统管理员：以“组织、账号、角色、集成、安全”为组织轴，默认不读取合同正文。
- 用章管理员保留为长期角色，但第一阶段没有工作项和业务入口。
- AI 附着在合同修订和业务动作上，不成为独立业务主轴。

## 3. 已确认的七个核心对象

| # | 核心对象 | 稳定身份与职责 | 包含的子记录 | 明确不是什么 |
|---:|---|---|---|---|
| 1 | 合同 Contract | 一项合同业务的稳定身份；承载编号、经办归属、阶段和关系 | 当前有效修订引用、合同关系、展示状态、审计索引 | 不另建“合同申请”；草稿就是合同的初始阶段 |
| 2 | 合同修订 ContractRevision | 一次可审查、可批准的完整合同快照 | 结构化字段、参与方快照、所引用的精确 DocumentVersion 集合、版本差异 | 不只是正文文件版本；不拥有或复制文档谱系 |
| 3 | 合同类型 ContractType | 合同分类及其发布版本，决定字段结构和基础行为 | ContractTypeVersion、字段 schema、分类属性、生效记录 | 不等于模板，也不吞并编号、权限和提醒规则 |
| 4 | 模板 Template | 可独立治理、发布和引用的公司范本身份 | TemplateVersion、变量、适用类型版本/主体/组织、发布记录 | 不是合同类型上的一个可覆盖附件 |
| 5 | 参与方目录 PartyDirectory | 我方主体、相对方及联系人的主数据目录 | PartyMaster、PartyImportJob、去重状态和失败回执 | 不管理系统用户、部门和角色；不回写历史合同快照 |
| 6 | 流程业务单族 WorkflowCase | CLM 中协同和合同审批的业务上下文；长期可扩展其他阶段 | 第一阶段使用 CollaborationCase、ContractApprovalCase；审批业务单保存 `submittedRevisionId`、`currentRevisionId`、`approvedRevisionId`、`supersedesCaseId`、重审路由引用、结果引用和 BPM binding，并用 ApprovalTaskRevisionBinding 保存 `taskId → decisionRevisionId` | 不复制 Flowable 的定义、实例、任务、意见和历史；任务—修订绑定不复制任务或正式意见；不塞入一张万能 type 表 |
| 7 | 重大承诺 Commitment | 合同约定中需要结构化声明和后续追踪的事项 | 内容、责任人/部门、期限；第一阶段只填写、校验并冻结到修订 | 不只是正文备注；第一阶段不执行履约、提醒或证据采集 |

### 3.1 支撑记录

- Document / DocumentVersion / DocumentBlob：归属合同的文档容器、不可覆盖版本和私有内容；合同修订只引用精确版本。
- WorkItemProjection：把 BPM 任务和 CLM 阶段任务统一投影为待办；它是查询模型，不是第二套任务事实。
- ContractRelation：原合同与变更、补充协议、续签、复制件、框架/子合同的有类型关系；第一阶段不启用处置流程。
- ContractAction：变更、续签、关闭、终止、作废的业务申请与结果；第一阶段后置。
- NumberingRule / WorkflowRouting / PermissionPolicy / ReminderRule：独立支撑配置，引用合同类型版本和适用组织。
- IdentityReference：部门、系统用户和角色复用 RuoYi 身份体系；修订只保存引用和必要历史快照。
- ContractParticipant：合同负责人、协同人、查看人及业务化权限；不替代产品角色和组织数据权限。
- AuditEvent：查看、编辑、下载、提交、审批、权限变化等追加式留痕。
- ReminderDelivery：规则触发后的消息、渠道、送达、升级与停止记录。
- AIReviewRun / Finding：对一个精确合同修订运行的摘要、抽取或审查结果及人工处理状态。
- ApprovalTaskRevisionBinding：CLM 持有的任务—合同修订唯一绑定；只记录 Flowable `taskId`、审批业务单和审批决定实际使用的 `decisionRevisionId`，不复制任务、意见或节点历史。
- SigningResult / ArchiveRecord：长期对象，第一阶段不创建、不展示、不生成任务。

WorkflowCase 只保存 CLM 业务上下文和 BPM 绑定；流程实例、任务、意见与审批历史继续由 BPM 持有。

### 3.2 术语表

| 采用术语 | 含义 | 弃用或避免的说法 |
|---|---|---|
| 合同 | 一项合同业务的稳定身份 | 合同申请、审批单就是合同 |
| 合同修订 | 正文、关键字段和参与方组成的完整可审查快照 | 合同版本（会与文件版本混淆） |
| 文档版本 | 一份文件内容的不可覆盖版本 | 用文件版本代替完整合同修订 |
| 协同 | 提交审批前，业务和法务围绕修订进行修改、评论和确认 | 把协同等同于审批 |
| 合同审批 | 对精确合同修订作出内部批准决定的流程 | 审批通过即已签订 |
| 工作项 | 从 BPM 或 CLM 业务阶段投影到个人工作台的可处理事项 | 再造一套审批任务 |
| 合同管理员 | 管理合同类型、模板、规则、主数据和业务数据范围 | 万能管理员 |
| 系统管理员 | 管理组织、账号、角色、集成与安全 | 默认可看所有合同正文的超管 |

## 4. 对象关系

~~~text
ContractType ──发布 TypeVersion ──约束──> Contract
Template ──发布 TemplateVersion ──适用于──> ContractTypeVersion
Contract ──拥有──> Document ──拥有──> DocumentVersion
Contract ──拥有──> ContractRevision ──引用──> DocumentVersion 集合
ContractRevision ──引用 PartyDirectory 并冻结──> PartySnapshot
ContractRevision ──包含──> CommitmentSnapshot
Contract ──产生──> WorkflowCase ──绑定──> BPM instance/task/history
WorkflowCase / CLM stage ──投影──> WorkItemProjection
ContractRevision ──绑定──> CollaborationCase / ContractApprovalCase / AIReviewRun
Contract ──通过 ContractRelation──> 另一 Contract（第一阶段后置）
~~~

## 5. 已确认的角色

| 角色 | 默认数据范围 | 第一阶段核心动作 | 第一阶段不应拥有 |
|---|---|---|---|
| 业务经办人 | 我经办、我参与、组织授权的合同 | 模板/上传起草、维护相对方和字段、发起协同、处理意见、提交、撤回、查看审批结果 | 模板发布、全局规则、任意合同查看 |
| 法务 | 我待办、我协同、授权组织的合同 | 审查、在线修订、评论、完成协同；在审批节点同意、退回或拒绝 | 系统账号和集成配置 |
| 合同管理员 | 授权组织或全公司的合同元数据和治理数据 | 发布类型/模板/编号/路由/权限，导入相对方，处理规则异常；按数据权限查看台账 | 系统安全密钥、代替业务修改正文、代替审批人决策 |
| 系统管理员 | 组织、用户、角色、配置和安全日志 | 钉钉组织同步、账号生命周期、角色和数据范围授权、SSO/待办集成、同步审计 | 默认读取合同正文或成为合同全局经办人 |
| 审批人（流程身份） | 当前/历史参与的审批单及必要合同上下文 | 同意、退回、拒绝、转交、加审、评论；按节点授权编辑 | 独立的全局产品后台 |
| 用章管理员 | 第一阶段无业务数据范围 | 无 | 用章、签署、归档入口和任务均不在第一阶段生成 |

同一用户可同时拥有多个角色；数据权限叠加组织、合同类型、参与关系和字段规则。

## 6. 已确认的不变量

1. 合同身份稳定：审批不会新建另一份无关联合同。
2. 合同修订不可覆盖：正文、关键字段或参与方改变时生成新修订；每个审批意见绑定审批人实际看到的修订。
3. 模板独立版本化：新起草引用明确的已发布模板版本；历史合同和草稿不被新模板静默回写。
4. 工作台任务可处理、可审计，但不复制 Flowable 任务事实。
5. 系统管理员管理身份和系统不等于可读合同正文；排障使用显式授权和审计。
6. AI 结果绑定精确修订；修订变化后旧结果标记过期，可重新运行，不能静默沿用。
7. 所有审批节点的正文或关键字段编辑都生成新修订和差异。
8. 重大变化终止旧修订继续获批的资格：Flowable 旧实例进入 `CANCEL`，旧 ContractApprovalCase 进入 `CANCELED` 且终止原因为 `REVISION_SUPERSEDED`；新业务单通过 `supersedesCaseId` 指向旧单并绑定新修订。第一阶段默认从完整审批路线起点重启；只有发布并验收了独立“法务首审”重审路线时才允许从该路线启动，不在原实例内做任意跨分支跳转。此前审批记录保留但不冒充新修订的有效批准。
9. 第一阶段审批通过后不得自动创建用章、签署、归档或履约任务，也不得把合同状态显示为已签订、已生效或已归档。

## 7. 第一阶段边界

### 7.1 纳入

- 标准模板起草。
- 非标文件上传、字段补全和法务协同。
- 合同修订、差异、评论和 AI 审查侧栏。
- 合同提交校验、提交时编号、业务单据流程配置、合同审批和完整审批历史。
- 重大承诺的结构化声明、“无重大承诺”显式确认及提交校验；不做履行。
- 模板、合同类型、编号、业务单据流程配置、权限的最小治理流程；面向用户分别通过“模板管理”“基础设置”“工作流设置”进入。
- 合同域流程定义的可视化节点、审批人和条件分支配置；保存草稿并发布为新的 Flowable 定义版本。
- 相对方批量导入。
- 钉钉组织同步、审批待办推送和带身份跳转。
- 起草到审批完成范围内的审计留痕。

### 7.2 明确后置

- 用章审批、印章管理、纸质或电子签署、CA、印控设备和回调。
- 最终签署件上传、归档确认、归档提醒。
- 合同生效、履约执行、承诺提醒与证据、到期提醒。
- 变更、续签、关闭、终止和作废流程。
- 收付款、结算、发票和财务系统联动。
- 综合法务域、客制化报表和通用低代码平台。

客户附件中的用章、纸质签约和归档仍保留在总需求池；它们只是后置，不是取消，也不能用预留按钮或空页面宣称完成。

## 9. 业务流程

### 9.1 第一阶段完成定义

第一阶段的唯一业务终点是：

**同一 Contract 下存在一个已完成的 ContractApprovalCase，其批准结果绑定一个不可覆盖的 ContractRevision；该修订、审批意见、历史实例和操作日志均可追溯。**

审批完成后只发送结果通知，不创建任何后续阶段任务。

### 9.2 按角色枚举的完整旅程

| 角色 | 如何发现/触发 | 主要过程 | 失败与恢复 | 如何得知结果 |
|---|---|---|---|---|
| 业务经办人 | 从工作台主动新建，或收到协同完成、退回、拒绝、审批结果待办 | 选模板或上传文件 → 选参与方 → 填字段/承诺 → AI 辅助 → 发起协同 → 处理意见 → 提交 → 跟踪审批 | 校验失败保留草稿；路由/编号失败可修复重试；退回、拒绝、撤回后在同一合同下产生新修订并重提 | 工作台与钉钉显示当前处理人、原因、修订、完整时间线和最终审批结果 |
| 法务 | 收到待协同或审批节点任务 | 查看背景/正文/字段/历史差异 → 在线修订、评论、处理 AI 风险 → 完成协同或作审批决定 | 修订变化使旧结论过期；并发编辑需比较/合并；离职或无权限可转交 | 能看到意见绑定的修订、业务是否采纳、下一处理人和审批最终结果 |
| 审批人 | 从工作台或钉钉深链打开本人任务 | 查看摘要、正文、字段、差异、附件、AI 风险和历史 → 同意/退回/拒绝/转交/加审；按权限编辑 | 重复操作幂等；重大编辑生成新修订并按规则重审；任务已转交/撤回时禁止继续处理 | 操作后显示生效结果、下一节点；历史中保留本人实际审阅版本 |

### 9.8 状态与事实边界

合同领域生命周期第一阶段只使用 DRAFT → APPROVED。为方便用户理解，界面从 CLM 与 BPM 事实计算以下展示阶段，不再把它们复制成另一套流程状态：

~~~text
DRAFT（草稿）
  → COLLABORATING（协同中）
  → READY_TO_SUBMIT（待提交）
  → IN_APPROVAL（审批中）
  → APPROVED（审批通过，第一阶段终点）
~~~

审批动作必须区分，不统一压成“撤回/退回状态”：

- 退回：Flowable 运行实例继续，只把任务退到流程图中串行可达且已验收的指定节点；保留实例和意见。第一阶段不承诺跨任意并行网关退回。
- 拒绝：当前审批实例结束；合同回到可修订状态，重提创建新审批实例。
- 发起人撤回：Flowable 实例进入 `CANCEL`，ContractApprovalCase 状态为 `CANCELED`、原因为 `STARTER_WITHDRAWN`；合同回到可修订状态。
- 版本替换取消：重大变化使 Flowable 旧实例进入 `CANCEL`，旧 ContractApprovalCase 状态为 `CANCELED`、原因为 `REVISION_SUPERSEDED`；新业务单通过 `supersedesCaseId` 指向旧单。
- 审批人撤回已办任务：仅在流程配置允许且下一节点尚未办结时撤回本人决定，流程仍为运行中，不等同发起人取消。
- 作废：属于后续 ContractAction，不用“拒绝”隐式代替。

事实所有权：

| 事实 | 唯一事实源 |
|---|---|
| 合同、修订、文档、参与方快照、重大承诺声明、编号、提交前协同评论与结论 | CLM |
| BPM 定义、流程实例、任务、正式审批意见、节点历史 | Flowable/BPM |
| CLM 业务单与 BPM 的绑定、提交/当前/获批修订、业务结果引用 | WorkflowCase |
| 每个 Flowable 任务作出审批决定时实际使用的合同修订引用 | ApprovalTaskRevisionBinding（`taskId → decisionRevisionId`） |
| 跨来源个人待办列表 | WorkItemProjection，只做投影 |
| AI 运行、发现项、处理状态和过期标记 | AIReviewRun / Finding |

审批任务详情、审批历史和合同业务时间线采用联合查询：CLM 提供修订、协同与业务单关系，Flowable 提供正式任务、意见与节点历史。正式审批意见不复制为 CLM 的第二份权威事实。

### 9.9 异常处理

| 异常 | 处理原则 | 不允许 |
|---|---|---|
| 模板/类型停用或起草期间发布新版 | 已有草稿继续锁定原版本；明确提示可升级；升级生成新修订 | 静默替换正文或回写历史合同 |
| 文件损坏、加密、超限、格式不支持、上传中断 | 不生成半成品正文；保留明确错误并安全重试 | 把失败文件当作可审批正文 |
| 多文件上传 | 必须指定一份正文，其余为附件 | 多份正文没有主次 |
| AI 超时/失败 | 人工流程继续；显示失败并允许重跑 | 因 AI 不可用阻断起草或审批 |
| 相对方缺失、失效或重复 | 草稿保留；进入主数据补录/合并流程，提交前阻断 | 临时自由文本绕过主数据和快照 |
| 重大承诺为空 | 必须填写事项或显式确认“无重大承诺” | 用空值代表“没有” |
| 并发编辑或回调超时 | 每次写入携带 baseRevisionId/baseDocumentVersionId 做乐观并发校验；冲突时保留最后成功版本并要求比较/合并 | 后保存者静默覆盖 |
| 协同完成后再次修改 | 新建修订；旧协同结论与 AI 结果过期，按规则重新确认 | 沿用旧结论 |
| 编号或流程启动部分失败 | 提交操作幂等；不得创建重复编号/实例；异常可对账修复 | 出现“有编号但无可恢复审批”或重复流程 |
| 路由零命中、多命中、审批人为空 | 阻断提交并生成合同治理异常 | 隐式走默认流程或自动通过 |
| 发起人撤回 / 审批人撤回已办 | 分别调用“取消实例”和“撤回本人任务”语义，并展示不同结果 | 共用一个无上下文的撤回状态 |
| 钉钉推送失败 | Web 待办仍有效；消息重试并去重 | 回滚已经创建的审批实例 |
| 审批人离职/无权限 | 进入任务交接异常；具有独立重分配权限的合同管理员选择合格接手人、填写原因，并通过受控服务端操作仅重分配活动任务，保留原 assignee 和审计 | 系统管理员擅自决定接手人，或冒充离职用户调用普通转交 |
| 状态回写失败 | 以 BPM 完成事实和绑定修订进行对账修复 | 仅改前端状态掩盖不一致 |

### 9.11 业务流程确认结论

业务流程已于 2026-08-27 确认：

1. 范本正文未改、必填校验通过且未命中强制法务规则时，业务可直接提交；其余场景必须先完成法务协同。
2. 合同编号首次成功提交后永久绑定；撤回、退回、拒绝后重提沿用原编号，编号永不回收。

模板草稿升级、重审锚点、经办人变更和相对方补录按本节规则执行，后续只细化操作、权限和页面归属，不再改变流程骨架。

### 10.10 角色 × 操作 × 数据范围

### 10.14 实施前技术门禁

以下事项会影响外部系统、安全、商用许可或真实流程验收，但不改变本功能清单，也不在当前阶段阻塞：

1. AI 模型供应商、合同数据能否出域、脱敏与日志留存要求。未确认前采用可替换适配层，禁止把真实合同发送到未授权外部模型。
2. 钉钉应用凭据、组织同步权限、SSO/待办回调域名。缺少真实凭据时只能完成适配和沙箱验证，不得宣称真实同步、登录或待办闭环通过。
3. 生产文档编辑器的部署位置、并发人数和商用许可。第一版继续复用现有 ONLYOFFICE 技术路径，但演示可用不等于获得生产许可。
4. 客户真实审批路线是否要求跨任意并行网关退回。快速复刻画布支持串行节点、条件分支、会签/或签和人工加审；在取得真实路线前，不宣称任意并行网关退回已经满足。
5. 审批中编辑与重审必须新增“当前任务 assignee + CLM 节点编辑预设”的服务端授权，并为 ContractApprovalCase 补齐 `submittedRevisionId/currentRevisionId/approvedRevisionId`、`supersedesCaseId` 和重审路由引用，为每个完成任务保存唯一 `taskId → decisionRevisionId`；完成前默认禁止审批中编辑，不能复用 BPM 表单字段权限冒充正文权限。
6. 首个真实租户上线前必须确认法务、合同管理员和节点编辑的数据范围；未显式配置一律拒绝，系统平台角色的全量数据范围不得穿透到合同域。
7. 正式编号公式、序列周期和并发唯一性需要用客户样例验收；未确认前只实现可替换的有限号段配置，并保持“首次成功提交永久绑定且不回收”的已锁定语义。
8. 离职活动任务交接需要新增受控的管理员重分配服务端操作：独立权限、仅活动任务、必填原因、保留原 assignee、追加审计，并验证接手人具备任务候选和合同上下文权限；不得冒充离职用户调用普通转交。

其余普通产品细节按一诺当前可见行为和本 PRD 的收敛规则处理，不再逐项询问。

### 10.15 功能清单确认结论

第一阶段共 42 个功能：33 个 P0、9 个 P1。原草案中的独立“统一异常队列”不保留为 F43：业务阻断由 F33 承接，导入/同步/消息失败分别在 F35/F37/F39 内恢复，流程一致性由 F42 对账。P0 先形成可运行核心闭环，P1 仍属于第一阶段目标，在 P0 后补齐。功能与流程双向追溯完整，角色权限和明确裁剪项均已列出，没有新的普通产品决策点。

### 11.1 端与职责区

第一阶段只有两个实际使用端，不拆成多套应用：

| 使用端 | 一句话职责 | 纳入 | 不纳入 |

桌面 Web 的领域职责仍分成三个区，但它们不再直接作为自造的侧边栏层级：

1. **合同工作区 W**：业务、法务和审批人处理“我的任务 + 合同”。
2. **合同配置后台 G**：合同管理员维护合同类型、模板、编号、流程、权限、相对方和业务异常；用户侧按一诺原词拆入审批管理、模板管理、基础设置、基础数据、工作交接事项和异常处理。
3. **系统管理 S**：系统管理员维护组织、产品角色和钉钉集成，默认不读取合同正文。

同一用户拥有多个产品角色时，顶部显示低存在感的“工作视图”切换：业务、法务、合同管理、系统管理。切换只过滤导航和工作台，不授予新权限；真正授权仍以 §10.10 的服务端公式为准。审批人是流程身份，不单列工作视图；只要存在当前或历史任务关系，审批中心和必要合同上下文按权限出现。

登录后一次性注册本人全部已授权路由。切换工作视图只过滤菜单树和 W01 查询分组，不删除路由、不重建权限缓存；钉钉或站内深链通过服务端鉴权后，即使目标入口在当前视图中被隐藏，也必须可打开，并可提示切换视图，不能因为视图不匹配返回 404。

### 11.5 两个核心工作屏

#### W04 合同工作区

| 区域 | 内容 | 规则 |
|---|---|---|
| 顶部 | 合同名称、编号、展示阶段、负责人、当前修订和主动作 | 只出现当前阶段可执行动作；审批通过后没有签署/归档按钮 |
| 中央文档区 | 正文预览/编辑、缩放、版本提示和差异入口 | 正文与合同修订分层；每次保存生成不可覆盖版本和新修订 |
| 右侧信息区 | 基础信息、参与方、重大承诺、附件、修订历史、业务时间线 | 编辑权限按阶段与角色收敛；无权字段不渲染 |
| 上下文工具栏 | AI、协同、审批进度 | 只在有上下文时出现；AI 结果和协同结论绑定当前修订并显示过期态 |

W02 选择模板或上传成功后先创建草稿，再进入 W04；创建和后续编辑不是两套信息结构。W03 的“已删除草稿”打开 W04 墓碑只读态，仅草稿所有者可执行恢复。W05/W06 打开合同时复用同一文档与信息组件，但动作由协同任务或审批任务决定；获授权合同管理员从 W04 审批区进入 W06 合同历史模式，只能查看不能代替审批人操作。

#### W06 审批中心

W06 是合同审批唯一业务入口，拥有两种互斥上下文：`taskId` 任务模式负责 `taskId → decisionRevisionId` 和任务动作，`contractId` 合同历史模式只读展示授权范围内的审批事实。旧的通用 BPM 合同详情必须跳转或直接渲染 W06，不能保留第二套合同审批动作与状态刷新逻辑；通用 BPM 详情继续服务非合同流程。

| 区域 | 桌面 Web | 钉钉窄屏 |
|---|---|---|
| 任务导航 | 左侧任务列表 + 顶部四个范围 Tab | 单任务标题 + 返回钉钉待办 |
| 任务内容 | 右侧摘要、修订差异、正文/附件、审批历史、评论 | 摘要、关键字段、正文只读、历史折叠 |
| 动作 | 仅任务模式显示底部固定同意/退回/拒绝/更多，编辑进入同屏专注模式；合同历史模式不显示动作 | 仅任务模式显示底部固定基本审批动作；审批中在线改稿提示到桌面处理 |
| 反馈 | 显示实际生效结果、下一处理人和任务最新状态 | 完成后回写待办并展示结果，不自动关闭前丢失反馈 |

### 11.6 逐角色最高频点击路径

点击数按“从角色工作台进入到业务动作完成”的主要操作计算，不计字段录入、滚动和展开详情。

| 角色旅程 | 点击路径 | 主要点击数 | 完成与返回 |
|---|---|---:|---|
| 业务：标准模板直提 | W01“标准模板起草” → W02 选模板 → W04 保存并提交 | 3 | 留在 W04 显示编号、已提交修订和下一审批人 |
| 业务：非标上传并请法务协同 | W01“上传起草” → W02 选文件 → W04 发起协同 | 3 | 留在 W04 显示当前法务和等待时长；完成后工作台结果卡一击返回并提交 |
| 法务：处理协同 | W01“待我协同” → W05 打开首条任务 → 完成或要求修改 | 2 | W05 自动打开下一条；业务收到结果通知 |
| 审批人：处理合同审批 | W01/钉钉待办 → W06 任务详情 → 同意/退回/拒绝 | 2 | 显示实际结果与下一处理人；已办任务仍可回看决定修订 |
| 审批人：非重大编辑后审批 | W06 任务 → 审批中编辑 → 保存新修订 → 作出决定 | 3 | 当前任务继续，决定与新修订唯一绑定，随后显示实际结果 |
| 审批人：重大编辑触发重审 | W06 任务 → 审批中编辑 → 保存新修订 → 确认重新发起 | 3 | 原任务立即失效且不再显示决定按钮；旧业务单显示因修订替代而取消，新业务单按已发布重审路线启动 |

所有路径均有完成反馈、失败恢复和返回位置，不依赖用户去通用 BPM、数据库或运维菜单确认结果。

### 11.7 导航与状态规则

1. 工作台数字、列表 Tab 和通知使用同一查询口径；数字点击后必须带着筛选条件进入目标页。
2. W03/W05/W06 保留返回时的筛选、页码和当前任务，避免处理一条后从头查找。
3. 合同阶段只显示草稿、协同中、待提交、审批中、审批通过；退回是运行中任务动作，拒绝/取消后合同回到可修订，不新增伪生命周期。
4. 钉钉深链必须包含不可猜测的任务上下文，先完成 SSO，再由服务端校验当前/历史任务关系；失败时不泄露合同名称和正文。
5. W04/W05/W06 的正文、修订差异和审批历史来自共享查询组件，但正式审批意见仍以 Flowable 为唯一事实源。
6. 空态直接给出下一步：无草稿可去“合同拟制 → 合同起草”，无相对方可向合同管理员反馈，无已发布模板/路由则进入“异常处理 → 配置异常”；无权限只解释申请路径，不显示被隐藏数据。
7. 删除、发布、停用、合并、撤回、拒绝、重审和任务重分配均在动作附近说明后果并二次确认。
8. 工作视图不会隐藏跨角色紧急任务：全局待办角标、钉钉深链和 W01 的总待办始终按本人真实任务计算，视图只改变分组和菜单呈现。
9. P1 页面或动作在尚未可用时完全隐藏；不发布空菜单、占位按钮或点击后提示“暂未实现”的伪能力。
10. W03 的“已删除草稿”是恢复唯一入口；删除不移除审计事实，W04 恢复态在成功恢复前不允许编辑或提交。
11. G05 只发布合同域授权政策，S01 是用户有效授权的唯一写入口；两页不得修改同一份用户—组织—合同类型授权记录。
12. 合同流程在 W06 只有一个动作外壳；共享文档组件只展示合同事实，不能自行完成任务或刷新流程状态。
13. 旧完整路径只作为隐藏兼容别名并跳转到新路径，必须保留 query/hash；兼容路由不得形成第二个业务页面或第二份菜单授权。
14. “页面布局配置”只维护合同分类草稿版本的合同表单；不得以该名称恢复通用 BPM 表单、任意对象 schema 或脚本式低代码平台。

### 11.8 信息架构结论
